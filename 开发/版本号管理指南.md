# Miku Cure 版本号管理指南

为了保证项目在构建、打包、发行时版本号的一致性，防止碎片化，本项目实行**“以主 package.json 为准”**的版本管理策略。

## 版本号唯一真实来源 (Single Source of Truth)

本项目的核心版本号唯一来源为：

`frontend/package.json` 中的 `"version"` 字段。

任何涉及到应用程序界面展示、打包输出的文件名、以及后端调用的版本标识，都应该以此为基准同步。

当前约定采用语义化版本：`MAJOR.MINOR.PATCH`（例如 `1.1.0`）。

|  bump 类型 | 示例 | 何时使用 |
|-----------|------|----------|
| MAJOR | `1.x` → `2.0.0` | 破坏性协议/架构变更 |
| MINOR (`+0.1`) | `1.0.2` → `1.1.0` | 新功能（启动器、便携包、新引擎等） |
| PATCH | `1.1.0` → `1.1.1` | 缺陷修复、文案/依赖微调 |

发版时打 Git tag：`v` + 版本号，例如 `v1.1.0`。

## 发版必改清单（Checklist）

修改 `frontend/package.json` 的 `version` 后，**同步**以下位置（全文搜索旧版本号）：

### 1. 前端 / Electron

| 文件 | 字段 / 位置 |
|------|-------------|
| `frontend/package.json` | `"version"`（**主源**） |
| `frontend/package-lock.json` | 根包 `"version"`（两处：文件顶与 `packages[""]`） |
| `frontend/main.js` | `app.setAppUserModelId('MikuCure.DesktopPet.X.Y.Z')` |

设置页「关于」通过 IPC `get-app-version` → `app.getVersion()` 读取，**不要**在 HTML 硬编码。

### 2. 启动器（MikuCure-Launcher）

启动器是独立 PySide6 进程，**不会**自动读取 `package.json`，必须与主版本号对齐：

| 文件 | 字段 / 位置 |
|------|-------------|
| `launcher/core/paths.py` | `APP_VERSION = "X.Y.Z"`（窗口标题、关于页、状态栏） |
| `launcher/main.py` | `SetCurrentProcessExplicitAppUserModelID("MikuCure.Launcher.X.Y.Z")` |

**发版流程建议：**

1. 先改 `APP_VERSION` 与 AppUserModelID  
2. 再执行 `launcher/build.bat`（或 PyInstaller）生成根目录 `MikuCure-Launcher.exe`  
3. exe **不入库**（见 `.gitignore`），仅随便携包 / Release 资产分发  

> 注意：Windows 任务栏图标分组依赖 AppUserModelID。改版本号后用户会看到新的任务栏分组条目，属预期行为。

### 3. 后端 WebSocket 握手

| 文件 | 字段 / 位置 |
|------|-------------|
| `backend/main.py` | `backend_ready` 消息里的 `"version"` |
| `backend/websocket_server.py` | 若仍有硬编码 version，一并改掉 |

前端可用该字段做兼容性提示（可选）。

### 4. 便携包 / 脚本 / 文档

| 文件 | 字段 / 位置 |
|------|-------------|
| `package_portable.ps1` | 写入 `PORTABLE_MANIFEST.json` 的 `version` |
| `start.bat` | 横幅打印版本 |
| `install.bat` | 横幅打印版本 |
| `README.md` | badge：`version-vX.Y.Z` |
| `train/frontend/package.json` | 与主系统强绑定时同步 `"version"` |

### 5. Git

```text
git commit -m "chore: bump version to X.Y.Z"
git tag vX.Y.Z
git push origin main --tags
```

## 静态文件的硬编码约束

对于无法动态读取配置的静态脚本或独立环境（`.bat`、启动器 Python、README badge），需要在发布新版本时手动全局搜索并替换。

建议在未来增加 `scripts/bump_version.js`（或 `.ps1`）：以 `frontend/package.json` 为输入，批量替换上表路径，并可选调用启动器重建。

## 前端的动态版本号注入

在 Electron 前端中，**绝对禁止**在 HTML 中硬编码版本号（如 `<div class="about-ver">v0.2.1</div>`）。

正确的做法是：

1. 主进程（`main.js`）注册 IPC：

   ```javascript
   ipcMain.handle('get-app-version', () => {
     return app.getVersion();
   });
   ```

2. 渲染进程（如 `settings_renderer.js`）动态注入：

   ```javascript
   ipcRenderer.invoke('get-app-version').then(version => {
     document.querySelector('.about-ver').textContent = 'v' + version;
   });
   ```

采用此策略后，Electron 侧只需保证 `frontend/package.json` 正确，界面「关于」会自动更新。

## 启动器版本与主版本的关系

| 组件 | 版本来源 | 是否必须同号 |
|------|----------|--------------|
| 桌宠 Electron | `frontend/package.json` | 主源 |
| 启动器 GUI | `launcher/core/paths.py` → `APP_VERSION` | **应与主源相同** |
| 后端 ready 包 | `backend/main.py` 硬编码 | 应与主源相同 |
| 便携清单 | `package_portable.ps1` | 应与主源相同 |

原则：**一次发版，一个版本号，一个 tag**。不要出现「启动器 1.0.3、桌宠 1.1.0」这种分裂，除非做仅启动器 hotfix 并在 Release 说明中写清。

仅启动器 hotfix 时的例外流程：

1. 仍 bump 主版本 PATCH（例如 `1.1.0` → `1.1.1`），全表同步  
2. 或临时在启动器关于页标注 `1.1.0+launcher.1`，但 **不推荐**；优先走正式 PATCH

## 快速全局搜索

发版前在仓库根目录执行（PowerShell）：

```powershell
# 将 1.0.2 换成即将淘汰的旧版本
rg -n "1\.0\.2" -g "!node_modules" -g "!package-lock.json" -g "!开发"
```

确认除依赖包名外，业务硬编码均已替换为新版本。
