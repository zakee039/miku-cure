# Miku Cure v1.2.2 肢体追踪扩展：上肢姿态 feature 方案

> 日期：2026-09-01
> 基线：`v1.2.2` / `84fcabc`
> 项目：`E:\project\miku cure`
> 状态：独立预研方案；属于“肢体追踪”总开关下的未来 feature，不增加独立用户开关。

---

## 1. 结论先行

本方案的目标不是“识别到抬手后随便触发一个预制动作”，而是：

> **如果两个 Live2D 模型具备足够的独立肩/肘/腕连续参数，就实现用户上肢姿态到 Miku 上肢的连续镜像追踪；如果模型自由度不足，则该 feature 不做。**

当前环境已实机确认：

- `mediapipe 0.10.35`；
- `PoseLandmarker` 可用；
- `HandLandmarker` 可用；
- 当前只随程序打包了 `face_landmarker.task`；
- 两个 Live2D 模型都有肩膀、左臂、右臂、双臂、手指等 Parts；
- 两模型 `.cdi3.json` 可确认存在肩部相关参数 `Param28`；
- 但尚未证明存在完整、独立的左右肩—肘—腕连续参数链。

因此本方案只有一个硬 Gate：

```text
Phase 0 参数审计
├─ 参数自由度足够 → 继续 Pose 连续上肢追踪
└─ 参数自由度不足 → 停止，不发布上肢 feature
```

不提供“动作识别 → 比心/唱歌/其他无关预制动作”的降级替代。

产品入口保持：

```text
🫣 肢体追踪（唯一总开关）
├─ face feature       当前已有
└─ upperBody feature  参数审计通过后才加入
```

上肢 feature 不单独开关。

---
## 2. 为什么 Face Landmarker 不能直接做抬手

当前 `backend/face_tracker.py` 使用 Face Landmarker，输入和输出范围都集中在人脸：

- 头姿；
- 眼睛；
- 眉毛；
- 嘴部；
- blendshape。

它不知道：

- 肩膀在哪里；
- 手肘在哪里；
- 手腕在哪里；
- 手是否高于肩膀。

所以“面捕已经开了”不代表程序天然能判断抬手。

抬手应使用 MediaPipe **Pose Landmarker**，需要更细手势时再引入 **Hand Landmarker**。

---

## 3. 推荐架构

沿用 v1.2.2 已建立的共享 Camera Service，不新增第二个摄像头实例。

目标结构：

```text
                       ┌─ EmotionDetector ~2 Hz（表情识别开启时）
Camera Service 20 FPS ─┼─ FaceLandmarker 15~20 Hz（bodyEnabled + face supported）
                       └─ PoseLandmarker 10~15 Hz（bodyEnabled + upperBody supported）
                                      │
                                      ▼
                           UpperBodyTrackingFeature
                                      │
                                      ▼
                  左/右 shoulder → elbow → wrist 连续语义
                                      │
                         双手抬起等组合姿态自然产生
                                      │
                                      ▼
                            镜像语义与平滑映射
                                      │
                                      ▼
                             Live2D 连续上肢驱动
```

关键原则：

1. **摄像头只开一个。**
2. Face、Emotion、Pose 各自独立频率和消费游标。
3. `bodyEnabled=false` 或模型不支持 `upperBody` 时不运行 Pose Landmarker，不白占 CPU。
4. 使用 latest-frame 策略，不堆帧队列。
5. 首版目标就是连续上肢驱动；关节点姿态事件仅可作为内部状态/测试语义，不作为替代产品路径。

## 4. Phase 0：先做模型手臂参数审计

这是能否进入“连续手臂跟随”的硬前置。

### 4.1 当前已知资源

两个模型都存在：

```text
Param28      肩部相关参数（cdi3 名称为 x肩膀）
Part66       手臂
Part67       左臂(2)
Part70       左臂
Part42       双臂
Part69       手指
Part72       手指
Part43       左臂
Part50       右臂
```

但是：

> **Parts 只是绘制部件，不等于可直接写入的实时运动参数。**

需要确认 `.moc3` 暴露的参数中，哪些参数真正能控制：

- 左肩抬起；
- 右肩抬起；
- 左肘弯曲；
- 右肘弯曲；
- 左腕；
- 右腕；
- 双臂整体动作；
- 手指。

### 4.2 建议增加开发期参数探针

只做开发工具，不暴露给普通用户。

功能：

```text
选择参数 ID
→ 滑块从 min 到 max
→ 实时观察模型变化
→ 记录“这个参数实际控制什么”
```

输出一份每模型映射表，例如：

```json
{
  "leftShoulder": { "id": "ParamXX", "min": -1, "max": 1 },
  "rightShoulder": { "id": "ParamYY", "min": -1, "max": 1 },
  "leftElbow": null,
  "rightElbow": null
}
```

若模型只有“肩部整体移动”或“预制动作触发参数”，则不要硬做连续骨骼复刻。

## 5. Phase 1：Pose Landmarker 上肢骨架

### 5.1 新增模块

建议：

```text
backend/pose_tracker.py
backend/models/pose_landmarker_lite.task
```

首版优先使用 Lite 模型，目标是桌宠场景低 CPU 占用；如果精度不够再评估 Full。

### 5.2 首版只取上肢关键点

无需把完整人体骨架全部发给前端。

后端只保留：

```text
left_shoulder
right_shoulder
left_elbow
right_elbow
left_wrist
right_wrist
```

可选再保留：

```text
left_hip
right_hip
```

用于估计上身方向和肩部基准。

### 5.3 WebSocket 不发送完整原始 landmark 数组

建议输出压缩后的上肢语义：

```json
{
  "type": "upper_body_tracking",
  "valid": true,
  "sequence": 123,
  "left": {
    "shoulder": { "x": 0.0, "y": 0.0 },
    "elbow": { "x": -0.2, "y": -0.1 },
    "wrist": { "x": -0.3, "y": -0.5 },
    "visibility": 0.93
  },
  "right": {
    "shoulder": { "x": 0.0, "y": 0.0 },
    "elbow": { "x": 0.2, "y": 0.0 },
    "wrist": { "x": 0.3, "y": 0.2 },
    "visibility": 0.91
  }
}
```

也可以进一步只发计算后的语义角度，避免前端理解 MediaPipe 坐标。

## 6. Phase 2：建立稳定的双侧上肢关节点语义

### 6.1 关节点是连续追踪输入，不是单独的“抬手按钮”

首版至少使用：

```text
left_shoulder / right_shoulder
left_elbow    / right_elbow
left_wrist    / right_wrist
```

根据 Phase 0 实际发现的 Live2D 自由度，再决定是否需要髋部或更多点用于上身基准。

系统不预设只支持“左手抬起/右手抬起”三个固定事件。用户单手抬起、双手同时抬起、不同肘角等，应尽量由左右两侧关节点连续映射自然表现。

### 6.2 双手抬起

“双手抬起”必须覆盖，但不额外设计一个独立开关或特殊模式。只要左右两侧肩—肘—腕链均有效，双手抬起应当自然成为连续姿态追踪的一个组合状态。

如果需要用于测试或内部状态判断，可根据关节点定义：

```text
left wrist 相对 left shoulder 达到抬起阈值
AND
right wrist 相对 right shoulder 达到抬起阈值
→ both_hands_raised = true
```

具体阈值不在方案阶段硬编码，结合真实关节点数据和模型可承载范围标定。

### 6.3 镜像产品逻辑

继续使用整个 Miku Cure 的“照镜子”定义：

```text
用户左侧肩/肘/腕
→ 桌宠画面右侧对应上肢

用户右侧肩/肘/腕
→ 桌宠画面左侧对应上肢
```

垂直抬高/降低保持同向；水平左右关系镜像。

## 7. Phase 3：连续上肢参数绑定

只有 Phase 0 已确认模型存在足够自由度时才进入本阶段。

绑定关系写入各模型 `miku-cure.config.json` 的 `tracking.upperBody` feature，不硬编码在 backend。

目标结构示意：

```json
{
  "tracking": {
    "upperBody": {
      "supported": true,
      "parameters": {
        "visualLeftShoulder": { "id": "..." },
        "visualLeftElbow": { "id": "..." },
        "visualLeftWrist": { "id": "..." },
        "visualRightShoulder": { "id": "..." },
        "visualRightElbow": { "id": "..." },
        "visualRightWrist": { "id": "..." }
      }
    }
  }
}
```

实际参数名与可用维度必须以参数探针结果为准，不能在方案阶段虚构。

如果最终只找到整体肩膀或预制动作触发参数，**本 feature 到此停止，不做“伪连续追踪”，也不退化为触发比心/唱歌等无关动作。**

## 8. Phase 4：连续手臂跟随实现

本阶段已由 Phase 0 Gate 决定：只有模型参数足够时才存在；否则整个 upperBody feature 终止。

### 8.1 Pose 可提供的连续数据

可以从肩、肘、腕计算：

```text
上臂相对水平线角度
前臂相对上臂角度
肩膀高度
手腕相对肩膀位置
```

例如：

```text
shoulderAngle = angle(shoulder → elbow)
elbowAngle    = angle(shoulder → elbow → wrist)
```

然后做归一化、镜像和平滑，再映射到 Live2D 参数。

### 8.2 但 Live2D 模型必须有对应自由度

如果参数审计发现模型只有：

```text
一个肩部参数
+ 几个预制动作触发参数
```

那么 Pose 即使算出了完整手臂角度，也没有足够的 Live2D 参数承载。

这种情况下直接判定 upperBody feature 不可实现并停止，不发布动作触发替代。

### 8.3 平滑建议

如果连续跟随可行：

- Pose 输入 10～15 Hz；
- 前端渲染按显示刷新率插值；
- 肩膀较慢；
- 手腕较快；
- 使用 EMA 或 One Euro Filter；
- 对关键角度设置死区；
- 丢失一只手时只释放该侧参数；
- 丢失全身时平滑回默认姿态。

## 9. Hand Landmarker 不属于当前 upperBody feature

Pose Landmarker 可以解决“抬手、挥手、手臂大姿态”。

如果未来要识别：

- 握拳；
- 张开手掌；
- OK；
- 剪刀手；
- 比心；
- 指向；

再引入 Hand Landmarker。

但当前模型是否能实时驱动每根手指还没有证据，因此首版不建议一开始同时跑 Face + Pose + Hand 三套 Landmarker。

推荐顺序：

```text
Pose 抬手稳定
→ 模型动作绑定稳定
→ 再考虑 Hand 手势
```

## 10. 摄像头与性能策略

当前 v1.2.2 已实现共享摄像头，本方案必须沿用。

推荐：

```text
Camera       20 FPS
Face         15~20 FPS（开启面捕时）
Pose         10~15 FPS（开启上肢追踪时）
Emotion      ~2 FPS（开启表情识别时）
```

如果只开抬手识别：

- 摄像头可不必强制 20 FPS，按 Pose 所需帧率调整；
- Pose worker 只保留最新帧；
- 不允许后台积压 landmark 推理任务。

如果 Face + Pose 同时开启：

- 两者共享同一 `CameraSnapshot`；
- 各有独立 sequence cursor；
- 不复制创建第二个 `cv2.VideoCapture`；
- 如 CPU 压力过大，优先降低 Pose 到 10 Hz，而不是降低面部眨眼/口型体验。

---

## 11. 摄像头画面要求

Face Landmarker 只需要脸，但 Pose 抬手需要至少看到：

- 双肩；
- 肘部；
- 手腕。

因此实际使用时用户可能需要坐得比纯面捕稍远。

需要处理：

```text
脸能看到，但手腕出画
→ Face valid
→ Pose 单侧/双侧 invalid
```

不能因为手出画就让面捕一起失效。

Face 和 Pose 的 valid 状态必须完全独立。

---

## 12. 隐私边界

继续沿用现有本地处理原则：

- 摄像头原始帧不上传；
- 不默认存储人体 landmark；
- WebSocket 只在本机环回地址传递语义数据；
- 不记录可还原人体动作轨迹的长期日志；
- 关闭最后一个 Camera consumer 后释放摄像头。

---

## 13. 与现有功能的仲裁

上肢动作会和模型现有动作发生冲突，例如：

- 唱歌；
- 比心；
- 大葱；
- 点击手臂触发动作；
- idle motion。

因此动作优先级建议：

```text
普通 Pose 姿态/抬手
< 用户显式点击动作
< 唱歌/业务强动作
```

当强动作开始时：

- 暂停该侧上肢连续参数；
- 不需要关闭 Pose Landmarker；
- 强动作结束后平滑恢复当前真人姿态。

如果只做离散抬手事件，则应加 cooldown，避免用户一直举手导致同一个动作不断重复触发。

## 14. UI 与用户开关

本方案**不新增任何用户按钮**。

正式入口继续只有：

```text
模型编辑
├─ 🖼️ 水印
├─ 🖱 鼠标追踪
└─ 🫣 肢体追踪
```

`🫣 肢体追踪` 对应统一的 `bodyEnabled`。开启时，运行该模型已经支持的全部肢体 feature：

```text
face       → 当前已有
upperBody  → 仅在本方案 Gate 通过并实现后加入
```

若上肢参数审计失败，则模型的 `tracking.upperBody.supported` 保持 false/不存在，用户仍可正常使用现有面部 feature；UI 不显示一个不可兑现的“上肢追踪”独立按钮。

- [ ] 不联网也能运行；
- [ ] 左右肩、肘、腕稳定输出；
- [ ] 一只手出画时不会令另一只手和 Face 一起失效。

- [ ] 左侧肩/肘/腕连续参数稳定；
- [ ] 右侧肩/肘/腕连续参数稳定；
- [ ] 双手同时抬起时两侧可同时连续响应；

- [ ] 用户左手 → 桌宠画面右侧响应；
- [ ] 用户右手 → 桌宠画面左侧响应；

- [ ] Face + Pose + Emotion 可共享一个摄像头；

### 连续手臂跟随（仅当模型参数足够）

- [ ] 左右肩独立；
- [ ] 左右肘独立；
- [ ] 镜像方向正确；
- [ ] 动作平滑，无高频抖动；
- [ ] 强动作期间仲裁正确；
- [ ] 丢手后平滑回默认姿态。

## 17. 最终推荐与决策 Gate

本方案只接受“方案 1”：

```text
模型自由度足够
→ Pose Landmarker
→ 双侧肩/肘/腕连续语义
→ 照镜子映射
→ Live2D 上肢连续跟随
```

如果 Phase 0 不能找到足够的左右独立连续参数：

```text
→ 终止 upperBody feature
→ 不做
```

不提供动作触发降级，不为了“看起来实现了”而绑定比心、唱歌、大葱或其他无关动作。

“双手抬起”不是独立模式，而是双侧关节点连续追踪自然形成的组合姿态；具体表现以实际可用关节点和 Live2D 参数自由度为准。

---
## 18. 一句话定义

> **上肢只是“肢体追踪”的一个内部 feature：模型自由度足够就做连续镜像追踪，参数不足就不做，不设置独立开关，也不提供动作触发替代。**
